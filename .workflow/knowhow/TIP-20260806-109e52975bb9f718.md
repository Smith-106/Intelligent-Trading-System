# OKX meta 端点真实行为核验（funding/OI 历史拉取）

## 适用场景
从 OKX 拉取 funding-rate 与 OI 历史数据时，必须遵守端点参数约束与覆盖上限。

## 已核验约束（2026-08-06 实测）

1. **funding-rate-history**：单页 limit 上限 **100**（请求 >100 → OKX 51000 "Parameter limit error"）。
2. **funding-rate-history 调用签名**：ccxt `fetchFundingRateHistory(symbol, since, limit, params)` —— limit 必须是 int；把 `{"limit": N}` 当第三参传会导致 URL 编码成 `limit={'limit': 100}` → 51000。这是 s3_verify 旧 funding 数据仅 63 行的根因（funding 历史下载从未在真实 API 成功过）。
3. **rubik OI-volume 端点**（`/api/v5/rubik/stat/contracts/open-interest-volume`）：begin+end **必须成对**（单传 begin 或 end → 50030 "Illegal time range"）；`after` 分页参数实测被忽略（begin+end 整窗返回）。
4. **OI 覆盖上限**（period 粒度）：1H 仅最近 ~30 天（720 行/h）；1D 覆盖 ~180 天。想拉 180 天请用 period=1D，不是 1H 分页 —— 修正了 spec:architecture-constraints-033 "OI 180 天经 period=1H 分页可达" 的说法。
5. **OI 响应结构**：rubik 端点返回 `[ts, oiUSD, volumeUSD]`，ccxt 解析后 OI 值在 `openInterestValue`（USD），`openInterestAmount` 为 None，`info` 是 **list 而非 dict** —— `info.get("oi")` 会 AttributeError。
6. **funding 结算周期**：BTC-USDT-SWAP 为 8h（90 天 ≈ 270 个结算点），非小时。

## 实现要点
- funding 分页：`effective_limit = min(limit, 100)`；页满判定用 effective_limit；end 守卫；MAX_PAGES 保护。
- OI 拉取：`fetchOpenInterestHistory(symbol, period, since, 1000, {'until': end})` 单窗口调用（ccxt since→begin、until→end）；limit 传大值防 ccxt 客户端切片。
- 对齐：funding 按 funding_time asof 向后对齐到小时 bar（结算点掩码 `funding_settle`），OI 直接 asof。
